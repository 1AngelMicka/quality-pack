# SaaS: accounts, subscriptions and activation: build rules

Apply these rules while you build. Domains or criteria whose `applies_if` flags are false in `.quality/project.json` do not apply to this project. Before you call a task done, check your work against the criteria of the domains you touched: each one must be true and verifiable.

If a stack module of the quality pack is installed (qp-nextjs, qp-node-api, qp-vps, qp-expo, qp-capacitor, qp-tauri, qp-electron), its rules skill adds stack-specific rules on top of these.

## Accounts, teams and access (ACC)

Isolation between customers, roles, invitations and the account life cycle.

Applies when: User accounts and login.

Rules:

- Set the customer model (single account, or organisation with members) and the data isolation before the first feature; write the two-account test at the same time.
- Isolate in the data layer (row-level security or access always scoped by customer), not route by route: a forgotten route must not be able to leak.
- A customer identifier sent by the browser is only a selector: the server re-checks membership on every request.
- Carry the customer into everything that leaves the request: cache keys, background jobs, file paths, signed links, search indexes, exports.
- Authentication through a maintained library or identity server; never hand-written crypto or sessions.
- Roles belong to the membership, not to the user; every privileged action is checked server-side.
- SSO, SCIM, custom roles, one database per customer: only when a customer contract asks for it.

Done means:

- [BLOCKER] ACC-01: Data isolation enforced in the data layer (only if: has_db). Check: Every customer-scoped table carries its key; no table without a policy (RLS) or mandatory scoped access; the database role is neither superuser nor BYPASSRLS.
- [BLOCKER] ACC-02: The two-account test covers every kind of resource and runs in CI. Check: access.json: one check per kind of resource and per role declared in project.json › access, no leak, no unexplained "unclear"; the same check blocks deployment.
- [BLOCKER] ACC-03: The customer is carried outside the request (cache, jobs, files, search, exports). Check: Cache keys, background job payloads, storage paths, signed links (scope and lifetime), search queries and exports: each carries and re-checks the customer.
- [BLOCKER] ACC-04: Authentication handled by a maintained library or service. Check: Authentication dependency identified, licence and latest release under a year old; no hand-written hashing, tokens or sessions.
- [major] ACC-05: Email verified before any sensitive action; single-use, short-lived links and codes. Check: Unverified account: no invitation, no card-less trial. Reset link or code: random, usable once, expired within 10 minutes to 1 hour, and does not bypass two-factor.
- [major] ACC-06: Two-factor available, sessions listed and revocable. Check: TOTP or passkey offered; list of active sessions with remote sign-out; changing email or password asks for authentication again.
- [BLOCKER] ACC-07: Roles checked server-side; the last owner cannot disappear (only if: multi_tenant). Check: Calling an admin route with a member account: refused. In an organisation with one owner: the owner cannot leave, be demoted or be deleted; ownership transfer exists.
- [BLOCKER] ACC-08: Invitations single-use, bound to the invited email, expiring and revocable (only if: multi_tenant). Check: Reusing an invitation, using it with another email, after expiry or after revocation: refused. An invitation never grants a higher role than the inviter's.
- [major] ACC-09: Removing a member or changing a role takes effect at once (only if: multi_tenant). Check: Remove a member, then replay a request with their old session and API keys: refused.
- [major] ACC-10: Log of sensitive actions, readable by the customer's admins (only if: multi_tenant). Check: Role change, export, deletion, support access: each leaves a line (who, what, when) that nobody can edit.
- [major] ACC-11: Support access to customer accounts is controlled. Check: No shared password or direct database access: time-boxed impersonation, visible banner, log entry, reason entered.

## Subscriptions (SUB)

Trial, plans and limits, failed payments, plan changes, cancellation, invoices and taxes.

Applies when: Recurring subscriptions with plans.

Rules:

- One source of truth for entitlements: a server-side table updated by the provider's signed webhooks, never by the browser or the return page.
- Every plan limit is enforced server-side, where the write happens; the interface only announces it.
- Webhooks: verify the signature on the raw body, answer 2xx fast, process once per event ID, accept any arrival order.
- Write the rules before the code: trial (length, card or not, what happens at the end), grace period after a failed payment, what happens to data after a downgrade.
- Test with the provider's test clocks: trial end, renewal, declined card, retries, cancellation.
- Taxes: collect the country and VAT number, configure the regime (EU one-stop shop, reverse charge) and check the country's e-invoicing duties.

Done means:

- [BLOCKER] SUB-01: Entitlements come from a server table updated by webhook, never from the browser. Check: Open the payment return address without paying, or send a changed plan from the browser: no entitlement granted.
- [BLOCKER] SUB-02: Every plan limit is enforced server-side. Check: Direct API call beyond the limit (projects, members, usage): refused with a clear message.
- [BLOCKER] SUB-03: Failed payment: email, in-app banner and a written grace period. Check: Test clock with a declined card: email with a link to fix the card, visible banner, access kept during the stated period then cut as written.
- [major] SUB-04: Trial: terms stated at signup, reminder before the end, defined end of trial. Check: Trial length and what follows visible before signup; reminder email a few days before the end; behaviour without a card tested.
- [major] SUB-05: Plan change: amount due now and at next renewal shown before confirming. Check: Preview compared with the invoice issued; a downgrade deletes no data without saying so.
- [BLOCKER] SUB-06: Cancellation online, in three steps at most from the account, confirmed by email. Check: Steps counted from the account settings; confirmation email with the effective date; no need to call or write.
- [major] SUB-07: Invoices in the account, country and VAT number collected, tax regime configured. Check: Sample invoice with the legal mentions; the provider's tax settings; written note on the country's e-invoicing.
- [major] SUB-08: Complete pricing page, identical to checkout (only if: public_web). Check: Price, period, unit (per member, per project), tax mention, limits in numbers, trial and cancellation rules; amounts compared with checkout.

## Activation and customer relationship (ACT)

First session, service emails, activation measurement, trust pages and customer exit.

Applies when: User accounts and login.

Rules:

- Name the activation event: the first time the user gets what the product promises. The whole first-run leads there.
- No blank screen on first launch: an empty state with one action, or sample data.
- Measure signup → activation → payment; billing events are recorded server-side.
- Write every service email before launch, in the product's voice and look, with a text version.
- The customer can leave with their data: machine-readable export and account deletion, self-service.
- Show no compliance badge (SOC 2, ISO, GDPR) that was not earned.

Done means:

- [major] ACT-01: A fresh account reaches activation in its first session. Check: A declared flow starts from a fresh account and reaches the activation event; no blank screen without an action; no forced tour.
- [major] ACT-02: Activation event defined and measured. Check: The event is named in project.json or the spec, and emitted in the code; the signup → activation → payment funnel can be read.
- [BLOCKER] ACT-03: Every service email exists (only if: has_email). Check: Trigger each: verification, reset, invitation, receipt, failed payment, trial ending, cancellation, account deletion. Each arrives, in the right language, with a text version.
- [major] ACT-04: Complete account settings. Check: Profile, security, notifications, billing, data export and account deletion are all there and work.
- [major] ACT-05: Public and accurate trust pages (only if: public_web). Check: Security page, data processing agreement and sub-processor list, status page, dated changelog; no unearned badge.
- [major] ACT-06: Five people from the target audience did the key tasks unaided. Check: Dated test report (user-testing skill): who, which tasks, where each got stuck, what was fixed since.
